## 3. HỢP ĐỒNG CÔNG KHAI (PUBLIC CONTRACTS)

### A. Cơ Sở Dữ Liệu Bảng `public.rooms` & 4 RPC Functions (Migration 0013)

```sql
-- Schema bảng rooms
CREATE TABLE public.rooms (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  code text NOT NULL UNIQUE CHECK (code ~ '^[23456789ABCDEFGHJKLMNPQRSTUVWXYZ]{6}$'),
  host_id uuid NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE,
  game_id text NOT NULL REFERENCES public.game_catalog(id),
  status text NOT NULL DEFAULT 'waiting' CHECK (status IN ('waiting', 'matched', 'cancelled', 'expired')),
  match_id uuid NULL REFERENCES public.matches(id) ON DELETE SET NULL,
  expires_at timestamptz NOT NULL DEFAULT (now() + interval '30 minutes'),
  created_at timestamptz NOT NULL DEFAULT now(),
  updated_at timestamptz NOT NULL DEFAULT now()
);

-- 4 RPCs SECURITY DEFINER
public.create_room(p_game_id text) RETURNS jsonb;
public.join_room(p_code text) RETURNS jsonb;
public.cancel_room(p_code text) RETURNS boolean;
public.get_my_room_status(p_code text) RETURNS jsonb;
```

## 4. QUYẾT ĐỊNH THIẾT KẾ TRONG PHASE

| Quyết định                                              | Lý do lựa chọn                                                                                                                                                                                                        | Phương án đã loại bỏ & Rủi ro                                                                                                            |
| :------------------------------------------------------ | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :--------------------------------------------------------------------------------------------------------------------------------------- |
| **Bảng chữ 32 ký tự an toàn**                           | Bỏ `O/0` và `I/1` giúp người chơi đọc mã cho nhau qua điện thoại/tin nhắn không bị nhầm lẫn. Không gian $32^6 \approx 1.07$ tỷ mã đảm bảo không bao giờ cạn mã.                                                       | _Dùng toàn bộ [A-Z0-9] (36 ký tự)_: Dễ nhầm giữa chữ O và số 0, chữ I và số 1.                                                           |
| **Atomic Optimistic State Transition khi Join**         | Câu lệnh `UPDATE rooms SET status='matched' WHERE code=? AND status='waiting'` là nguyên tử (Atomic). Nếu có 2 người cùng bấm vào 1 phòng, đúng 1 người cập nhật được dòng, người kia nhận `ROOM_TAKEN` ngay lập tức. | _Đọc SELECT rồi mới UPDATE_: Dễ bị Race Condition khi 2 người cùng đọc thấy 'waiting' và cùng gửi request join.                          |
| **Quyết định Không Optimistic khi đánh nước đi**        | Game đối kháng theo lượt (turn-based) chịu được độ trễ 300-800ms. Chờ server phản hồi giúp mã nguồn đơn giản, triệt tiêu 100% rủi ro lệch thế cờ hay rollback giật quân khi nước đi bị từ chối.                       | _Optimistic Move đặt quân trước trên client_: Dễ gây giật màn hình khi server từ chối nước đi (VD: sai lượt, ô đã có quân, mất kết nối). |
| **Broadcast 'move_accepted' là Nguồn Chân Lý Duy Nhất** | Cả 2 bên nhận cùng 1 gói tin broadcast có `stateSerialized` từ Trọng tài Server để cập nhật bàn cờ đồng thời. Client không tự áp move từ API response.                                                                | _Client tự áp move ngay khi nhận API response_: 2 bên cập nhật bàn cờ lệch nhịp nhau, dễ gây duplicate apply khi broadcast về sau.       |
| **Chống Áp Đôi & Idempotency**                          | So sánh nghiêm ngặt `payload.moveIndex === moveIndex + 1`. Gói tin có `moveIndex <= local` bị loại bỏ ngay lập tức.                                                                                                   | _Không kiểm tra moveIndex_: Có nguy cơ áp lại nước đi cũ khi mạng gửi lặp gói tin.                                                       |
| **Lưới An Toàn Auto-Resync khi Miss Broadcast**         | Khi phát hiện `payload.moveIndex > local + 1` (bị nhảy cóc do rớt gói tin mạng), hệ thống tự động gọi `matchRepository.getLiveState(matchId)` để kéo lại bàn cờ mới nhất từ DB.                                       | _Bỏ qua gói tin nhảy cóc_: Người chơi bị kẹt thế cờ cũ và không thể tiếp tục đánh các nước tiếp theo.                                    |
| **Tự động ngắt kết nối Transport khi Kết Thúc Trận**    | Khi `isGameOver = true`, hook `useMatchChannel` nhận `enabled = false` $\rightarrow$ ngắt kết nối WebSocket Realtime ngay lập tức.                                                                                    | _Giữ kết nối sau khi trận xong_: Lãng phí Quota Supabase Realtime Free Tier.                                                             |

## 7. ĐẦU VÀO GỢI Ý CHO PHASE KẾ TIẾP [PHASE P3.4: ĐỒNG HỒ CỜ, RESIGN & TIMEOUT]

1. **Hạ tầng đã sẵn sàng nạp cho P3.4**:
   - Cột `turn_deadline timestamptz NULL` đã có sẵn trong bảng `public.match_live_state`.
   - `system_config` có key `match.reconnect_window_seconds` (mặc định 60 giây).
   - Ván đấu online đã chạy mượt mà trên `OnlineMatchScreen.tsx`.
2. **Nhiệm vụ trọng tâm Phase P3.4**:
   - Kích hoạt `turn_deadline` trong Edge Function `referee` mỗi khi chuyển lượt (VD: 30s hoặc 60s cho mỗi nước đi).
   - Hiển thị đồng hồ đếm ngược (Countdown Timer) trực quan trên banner `OnlineMatchScreen.tsx`.
   - Thêm nút **"Đầu hàng / Nhận thua" (Resign)**: Gọi referee để xử thua ngay lập tức.
   - Thêm cơ chế **Xử thua do hết giờ (Timeout)**: Khi `now() > turn_deadline`, bất kỳ ai gọi `referee` đều kích hoạt xử thua bên quá hạn.
   - Dọn dẹp ván đấu treo (Abandonment cleanup).
