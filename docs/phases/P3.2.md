## 3. HỢP ĐỒNG CÔNG KHAI (PUBLIC CONTRACTS)

### A. Endpoint Edge Function Trọng Tài: `POST /functions/v1/referee`

Yêu cầu Header: `Authorization: Bearer <USER_JWT_TOKEN>`.

#### 1. Action `init` (Khởi tạo thế cờ)

- **Request Body**: `{ "action": "init", "matchId": "uuid-cua-tran-dau" }`
- **Response Thành Công (HTTP 200)**:
  ```json
  {
    "ok": true,
    "data": {
      "stateSerialized": "v1:15:5:0:1:0:0:-1:225.",
      "moveIndex": 0,
      "currentSeat": 0,
      "movesSerialized": ""
    }
  }
  ```

#### 2. Action `move` (Thẩm định nước đi)

- **Request Body**: `{ "action": "move", "matchId": "uuid", "moveSerialized": "112", "expectedMoveIndex": 0 }`
- **Response Nước Đi Hợp Lệ (HTTP 200)**:
  ```json
  {
    "ok": true,
    "data": {
      "moveIndex": 1,
      "moveSerialized": "112",
      "currentSeat": 1,
      "stateSerialized": "v1:15:5:0:1:1:1:112:112.x112.",
      "terminal": null
    }
  }
  ```
- **Response Nước Đi Trùng Lặp (Idempotent Duplicate - HTTP 200)**:
  ```json
  {
    "ok": true,
    "data": {
      "duplicate": true,
      "stateSerialized": "...",
      "moveIndex": 1,
      "currentSeat": 1
    }
  }
  ```

### B. Client API: `refereeRepository` (`src/repositories/refereeRepository.ts`)

```typescript
export interface RefereeRepository {
  initMatch(matchId: string): Promise<MatchLiveStateDto>;
  submitMove(
    matchId: string,
    moveSerialized: string,
    expectedMoveIndex: number,
  ): Promise<SubmitMoveResult>;
}

export type SubmitMoveResult =
  | {
      readonly kind: 'accepted';
      readonly moveIndex: number;
      readonly currentSeat: number;
      readonly stateSerialized: string;
      readonly terminal?: TerminalResult | null;
    }
  | {
      readonly kind: 'duplicate';
      readonly moveIndex: number;
      readonly currentSeat: number;
      readonly stateSerialized: string;
    }
  | {
      readonly kind: 'stale';
      readonly message: string;
      readonly moveIndex?: number;
      readonly stateSerialized?: string;
    };
```

- **Thứ tự sử dụng với `useMatchChannel`**:
  1. Người chơi vào phòng $\rightarrow$ `useMatchChannel` kết nối kênh `match:{matchId}`.
  2. Client gọi `refereeRepository.initMatch(matchId)` để nạp thế cờ ban đầu.
  3. Khi người chơi chạm vào bàn cờ $\rightarrow$ Gọi `refereeRepository.submitMove(matchId, moveSerialized, expectedMoveIndex)`.
  4. Cả 2 client nhận thông điệp Broadcast `move_accepted` từ `useMatchChannel` và áp dụng nước đi lên bàn cờ.

### C. DDL Bảng `public.match_live_state` & Ngữ Nghĩa `move_index`

```sql
CREATE TABLE public.match_live_state (
  match_id uuid PRIMARY KEY REFERENCES public.matches(id) ON DELETE CASCADE,
  state_serialized text NOT NULL,                    -- engine.serialize(state hiện tại)
  move_index int NOT NULL DEFAULT 0 CHECK (move_index >= 0), -- Số nước đã áp dụng (Khóa lạc quan + Idempotency)
  current_seat smallint NOT NULL CHECK (current_seat >= 0),   -- Ghế người chơi đang đến lượt đi (0-indexed)
  moves_serialized text NOT NULL DEFAULT '',         -- moves-codec tích lũy
  turn_deadline timestamptz NULL,                    -- Khai báo sẵn cho P3.4 đồng hồ đếm ngược
  updated_at timestamptz NOT NULL DEFAULT now()
);
```

- **Ngữ nghĩa `move_index`**:
  - `move_index = 0`: Ván cờ vừa khởi tạo, chưa có nước đi nào.
  - Mỗi nước đi thành công $\rightarrow$ `move_index = move_index + 1`.
  - Đóng vai trò là **Khóa Lạc Quan (Optimistic Lock)**: Client bắt buộc gửi `expectedMoveIndex`. Nếu `move_index` trên DB đã khác `expectedMoveIndex`, DB từ chối cập nhật dòng (`affectedRows = 0`), ngăn chặn triệt để xung đột ghi đè.

## 4. QUYẾT ĐỊNH THIẾT KẾ TRONG PHASE

| Quyết định                                                   | Lý do lựa chọn                                                                                                                                                                             | Phương án đã loại bỏ & Rủi ro                                                                                                   |
| :----------------------------------------------------------- | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------ |
| **Khóa Lạc Quan `move_index`**                               | Ràng buộc `WHERE move_index = expectedMoveIndex` đảm bảo mỗi nước đi được áp dụng tuần tự nghiêm ngặt, chống race condition khi 2 bên bấm cờ cùng lúc.                                     | _Khóa bi quan (Pessimistic Lock / SELECT FOR UPDATE)_: Giữ transaction dài làm chậm latency và dễ gây deadlock trên serverless. |
| **`duplicate` & `stale` là luồng bình thường (Không throw)** | Mạng di động thường xuyên bị chập chờn/gửi đúp hoặc lệch gói tin. Việc trả về `{ kind: 'duplicate' }` hoặc `{ kind: 'stale' }` giúp UI tự phục hồi mà không làm vỡ app với Error Boundary. | _Ném Exception cho duplicate/stale_: Khiến UI văng lỗi không cần thiết và làm gián đoạn trải nghiệm người dùng.                 |
| **Xóa `match_live_state` khi ván kết thúc**                  | Khi có người thắng/hòa, kết quả được finalize vào bảng `matches` (`final_state`, `moves`). Xóa live_state giúp tiết kiệm dung lượng Free Tier.                                             | _Giữ live state vĩnh viễn_: Phình bảng `match_live_state` theo thời gian.                                                       |
| **Tách biệt Logic Thuần (Core Pattern)**                     | Toàn bộ logic nghiệp vụ, thẩm định và khóa lạc quan nằm trong `core.ts` nhận dependencies inject, giúp chạy unit test trong Deno chỉ tốn 159ms mà không cần DB thật.                       | _Gộp toàn bộ vào index.ts_: Không thể viết automated test cho từng nhánh rẽ nếu không kết nối database thật.                    |
| **Settle Rating Elo & Xu hoãn lại tới Phase P4.2**           | Đã đánh dấu comment điểm gắn trong code finalize match. Giữ đúng phạm vi P3.2 tập trung hoàn toàn vào tính toàn vẹn của trọng tài server.                                                  | _Làm luôn rating ở P3.2_: Lẹm phạm vi, tăng độ phức tạp và rủi ro lỗi giao dịch.                                                |
